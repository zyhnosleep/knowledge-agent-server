# Knowledge Agent 开发与测试环境隔离设计

## 目标

在同一台双 GPU 服务器上建立完全隔离的开发环境与测试环境，统一模型组合，保留当前测试数据和公网入口，并彻底移除产品及运行资源中的旧 `wiki` 命名。

本次改造完成后：

- 开发环境固定使用 GPU 0，只能通过 SSH 端口转发访问，不启用应用登录。
- 测试环境固定使用 GPU 1，继续通过当前公网入口和临时账号访问。
- 两个环境分别拥有代码目录、API 服务、Ollama 服务、数据库、文件、向量、日志和运行配置。
- 两个环境均使用 `qwen3.5:9b` 生成答案，使用 `qwen3-embedding:4b` 生成检索向量。
- 前端不再提供“自动 / 快速 / 深度”模式选择。
- 开发版本只有在人工验收后才能发布到测试环境。

## 环境架构

### 开发环境

- 运行开发分支的最新已提交代码。
- 使用 GPU 0 上的独立 Ollama 进程，监听 `127.0.0.1:11435`。
- API 监听 `127.0.0.1:8002`。
- 使用全新的空数据库、空正式文件目录和空向量索引。
- 设置 `AUTH_ENABLED=false`，但 API 只监听回环地址。
- 不配置 Cloudflare Tunnel，只允许 SSH 本地端口转发。
- 开发服务的部署、停止、重启和故障不得影响测试服务。

### 测试环境

- 运行经过人工批准的固定 Git 提交，不自动跟随开发分支。
- 使用 GPU 1 上的独立 Ollama 进程，监听 `127.0.0.1:11436`。
- API 继续监听 `127.0.0.1:8001`。
- 保留当前项目、文章、原始文件、解析结果、账号、会话和审计数据。
- 继续使用当前临时公网入口、临时账号和公网密码保护。
- Cloudflare Tunnel 只转发测试 API，不暴露开发 API 或任何 Ollama 端口。

两个 Ollama 进程可以共享只读模型文件缓存。模型文件不包含业务数据，共享缓存可以避免相同模型重复占用磁盘；进程、端口、GPU、加载状态和请求队列仍完全隔离。

## 模型与资源配置

两个环境采用相同配置：

- 生成模型：`qwen3.5:9b`。
- Embedding 模型：`qwen3-embedding:4b`。
- 问答上下文：32K。
- Flash Attention：开启。
- KV Cache：`q8_0`。
- 生成并发：每个环境初始容量为 1，其他请求进入独立 FIFO 队列。
- 模型保留：最后一次生成或 Embedding 请求后保留 5 分钟，随后自动释放显存。
- 外部模型 API：保持关闭，问题和文档证据不发送给 DeepSeek。

GPU 绑定是硬约束。开发环境不得回落到 GPU 1，测试环境不得回落到 GPU 0，也不得在 GPU 不可用时静默切换为 CPU 推理。对应运行时异常时，健康接口和页面应显示明确的降级状态。

模型在显存中时状态为 `ready`，因五分钟闲置策略卸载后状态为 `idle`；两者均属于健康。模型缺失或 Ollama 不可访问时状态为 `degraded`。

## 问答与引用链路

问答链路固定为：

1. `qwen3-embedding:4b` 把用户问题转换为查询向量。
2. 后端检索服务从 pgvector 召回候选原文片段，同时保留文档 ID、文件名、页码、段落位置和相似度。
3. 后端证据整理器对候选片段去重、排序和截断，并分配稳定的证据编号。
4. `qwen3.5:9b` 只能根据已提供证据生成答案，并返回实际使用的证据编号。
5. 后端引用校验器删除不存在或越界的引用，将有效编号映射为文章名称、页码和原文件链接。

前端删除“自动 / 快速 / 深度”模式选择。停止生成、排队状态、检索过程、引用页码和来源链接继续保留。

## 数据迁移

测试环境切换期间启用维护模式，暂停上传、删除和 Agent 问答，避免新旧向量或迁移前后写入混用。

迁移步骤如下：

1. 备份当前 PostgreSQL 数据库并记录恢复命令。
2. 对原始文章目录和解析结果创建只读快照，并记录文件数量和哈希。
3. 将当前测试代码和数据迁入新的 `knowledge-agent-test` 正式目录和 `knowledge_agent_test` 数据库。
4. 将向量结构从 4096 维迁移为 `qwen3-embedding:4b` 对应的 2560 维。
5. 删除旧的 8B 向量记录，但保留文档、原始文件、解析文本、页码、项目关系和审计信息。
6. 使用 4B Embedding 为所有可检索文档重新生成向量。
7. 验证所有就绪文档均有完整向量，数据库中不存在旧维度或混合模型向量。
8. 完成质量验收后解除维护模式并恢复公网测试。

任何文档重建失败都阻止解除维护模式。原始文章始终是正式数据，不因迁移变成备份副本。开发环境直接创建新的 2560 维空向量结构，不迁移测试数据。

## 质量验收

迁移前从当前文章自动整理 15–20 个代表性问题，保存为固定验收集。验收至少覆盖单文档事实、多页证据、跨文档比较、无证据问题和中文长问题。

对比旧 8B 与新 4B Embedding 的以下结果：

- 正确文档是否进入 Top-K 召回结果。
- 正确证据片段的排名是否可接受。
- 引用页码、文章名称和原文件链接是否有效。
- 9B 回答是否忠于证据，是否出现无效引用。
- 冷启动、热状态总延迟、生成速度、GPU 显存和队列状态。

自动化测试、数据库完整性检查、模型运行时检查和页面验收全部通过后，才能恢复测试公网入口。

## 发布流程

发布链路固定为：

```text
开发分支提交
→ 自动测试
→ 部署开发环境
→ 页面与模型验收
→ 记录待发布 Git 提交
→ 备份测试数据库和文件
→ 启用维护模式
→ 人工发布到测试环境
→ 健康、数据和公网验收
→ 解除维护模式
```

测试环境不自动同步开发分支。每次发布都必须记录源提交、目标提交、数据库迁移、备份位置和回滚命令。

## 回滚与清理

- 新模型切换前保留数据库和文件快照。
- 当前 14B、27B 和 8B Embedding 模型文件保留 7 天，但不再加载到 GPU。
- 迁移失败时恢复上一 Git 提交、原数据库和原文件快照，并恢复旧模型配置。
- 新配置稳定 7 天且人工确认后，才允许删除旧模型和旧运行目录。
- 删除旧资源前再次核对 Git、Systemd、Cloudflare、数据库、备份和文档中不存在仍指向旧资源的活动配置。

## 完成标准

- GPU 0 只承载开发模型进程，GPU 1 只承载测试模型进程。
- 两套 API、数据库、文件、向量、日志和队列完全隔离。
- 两套环境均只使用 `qwen3.5:9b` 和 `qwen3-embedding:4b`。
- 测试环境现有数据完整，所有向量均为新模型生成的 2560 维向量。
- 开发环境无需登录且只能经 SSH 转发访问。
- 测试公网入口和临时账号继续有效。
- 前端不再显示模式选择，引用由后端验证后展示。
- 闲置五分钟后两个环境的模型可分别从对应 GPU 释放。
- 产品与活动运行资源统一使用 `Knowledge Agent` / `knowledge-agent` 命名。
- 固定验收集、全量自动化测试、健康检查和回滚演练全部通过。
