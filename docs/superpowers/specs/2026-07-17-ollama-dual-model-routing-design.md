# Ollama 双模型路由与流式问答设计

## 背景

当前测试服务器配备两张 NVIDIA RTX 3090（每张 24 GiB），问答链路使用 Ollama。专用向量模型为 `qwen3-embedding:8b`，生成模型包括 `qwen3:14b` 和 `qwen3.6:27b`。实测 27B 单次普通生成约 26 秒，最终结构化综合约 64 秒，完整 Agent 请求约 290 秒。

现有慢请求包含三个主要问题：模型曾分配 262K 上下文，远高于知识库问答需要；模型在请求完成后立即卸载；最终回答先要求结构化 JSON，格式不合规时会完整重试。现有 `/api/agent/query/stream` 已能传递阶段事件和最终结果，但尚不能逐 token 推送模型正文。

## 目标

- 默认提供“自动”模式，同时支持用户显式选择“快速”和“深度”。
- 快速模式固定使用 14B，深度模式固定使用 27B，自动模式按确定性规则路由。
- GPU 0 承载 14B 和专用 Embedding，GPU 1 承载 27B。
- 普通问答使用 16K 上下文，复杂问答使用 32K 上下文。
- 启用 Flash Attention、`q8_0` KV Cache、启动预热和 5 分钟闲置自动释放。
- 逐 token 流式输出 Markdown，完成后校验引用。
- 27B 繁忙时允许用户继续排队或切换快速模式，不静默降级。
- 在正常预热、无排队条件下，使普通问题在 30–60 秒内完成，复杂问题在 60–90 秒内完成。
- 保持文档上传、原始文件存储、解析、索引和引用数据兼容。

## 非目标

- 本阶段不引入 vLLM、Ray、Kubernetes 或新的模型格式。
- 不使用生成模型替代 `qwen3-embedding:8b`。
- 不重做文档解析或向量索引架构。
- 不把 CPU 混合推理作为正常服务路径。
- 不允许系统在用户不知情的情况下把深度请求改成快速请求。

## 推理服务架构

### GPU 0：快速生成与向量化

GPU 0 上的 Ollama 实例监听 `127.0.0.1:11435`，允许加载：

- `qwen3:14b`：快速生成模型，默认上下文 16K。
- `qwen3-embedding:8b`：唯一的 Embedding 模型。

Embedding 客户端拥有独立配置和调用接口，禁止从回答模式或生成模型名称推导 Embedding 模型。部署验收必须确认 14B 与 Embedding 同时加载后仍能完全放入 GPU 0。三种模型最后一次调用后均保留 5 分钟，随后自动释放显存，而不是回落 CPU。

### GPU 1：深度生成

GPU 1 上的 Ollama 实例监听 `127.0.0.1:11436`，运行 `qwen3.6:27b`，默认上下文 32K。模型最后一次调用后保留 5 分钟。深度模型初始并发容量为 1，其他请求进入应用层队列。只有基准测试证明更高并发不会导致 OOM、首 token 明显恶化或上下文缩水，才允许提升容量。

### 公共运行参数

两个 Ollama 实例均启用 Flash Attention 和 `q8_0` KV Cache。服务端和每个 API 请求统一设置 `OLLAMA_KEEP_ALIVE=5m`，确保最后一次生成或 Embedding 调用后 5 分钟自动释放显存。每个生成请求显式传递 `num_ctx`，不得依赖模型原生最大上下文或 Ollama 自动推断。

启动就绪条件包括：Ollama 端口可访问、所需模型存在、预热请求成功、生成模型显示为完全 GPU 装载、Embedding 维度为 4096。任一条件失败时，业务健康状态必须显示模型未就绪。

## 回答模式与路由

公开回答模式为：

- `auto`：默认模式，由服务端路由。
- `fast`：强制使用 14B。
- `deep`：强制使用 27B。

自动路由沿用现有 `PolicyRouter` 的确定性分类，不新增一次 LLM 路由调用：

- `simple_rag`：14B。
- `evidence_required`：默认 14B；同时命中多文档、复杂比较或深度分析规则时升级到 27B。
- 普通单文档摘要和一般证据问答：14B。
- `table_or_metric`：27B。
- `multi_source_compare`：27B。
- `complex_multi_hop`：27B。
- 明确要求深入分析、综合多篇文章、复杂比较或论证的问题：27B。
- `needs_clarification`：不调用生成模型，直接请求用户补充问题。

路由结果包含请求模式、实际模式、模型、上下文和路由原因，并写入 Agent trace。模型不可用时返回明确错误；自动模式可以告知另一模型可用，但只有用户确认后才能改用另一模式。

## 会话状态

回答模式是会话级状态：

- 新建聊天的初始模式始终为 `auto`。
- 用户切换后，同一会话后续请求沿用该模式。
- 刷新或重新打开历史会话时，从服务端恢复模式。
- 新建另一个聊天不会继承上一个聊天的选择。

服务端是会话模式的权威来源。前端可做即时显示，但不能只依赖 `localStorage`。每条回答记录请求模式、实际模型和路由原因，确保历史记录可解释。

## 流式回答协议

现有 SSE 接口 `/api/agent/query/stream` 扩展以下事件：

- `start`：请求标识、会话和模式。
- `route`：实际模型、上下文和路由原因。
- `queue`：模型忙碌状态、队列位置和可选操作。
- `step`：检索、证据整理等既有 Agent 阶段。
- `token`：模型生成的 Markdown 文本增量。
- `citation`：完成后的有效引用映射。
- `final`：完整回答、模型、引用和性能数据。
- `error`：错误类型、是否可重试和用户可执行操作。

最终综合不再先生成完整 JSON。模型直接流式输出 Markdown，并使用 `[0]`、`[1]` 等提供的证据编号。生成完成后，服务端解析回答中的编号，移除越界、重复或不存在的索引，再绑定文档、页码和原文链接。引用校验前，前端显示不可点击的临时编号；校验成功后替换为可点击引用。

客户端断开连接或用户点击“停止生成”时，服务端取消排队或终止对应 Ollama 流。已生成内容保留为未完成回答，不伪装为完整答案。

## 排队与多人使用

应用层为快速模型和深度模型分别维护有界队列及并发信号量。初始容量通过基准确定；深度模型默认单并发。

当 27B 繁忙时，前端显示“深度模型正在处理其他请求”，并提供：

- “继续等待 27B”：进入或保持队列。
- “立即切换快速回答”：取消尚未开始的深度任务，以同一问题重新提交 14B 请求。

队列显示前方任务数量，不显示未经校准的预计分钟数。切换模型必须由用户明确触发，并在 trace 中记录。用户离开页面、停止请求或会话失效时，队列项必须及时移除。

## 页面交互

聊天顶部显示三段式选择器：`自动｜快速｜深度`。每条回答旁显示实际执行信息，例如“自动 · 14B”或“深度 · 27B”。

回答过程中依次显示：分析问题、检索知识库、找到证据、等待模型、使用指定模型生成、校验引用和完成。收到首个 `token` 后立即显示正文，阶段信息收起为紧凑状态。页面提供“停止生成”。网络中断时保留已接收内容，并提供重新连接或重新提问操作。

模型错误不得转换成看似正常的固定模板。页面应明确区分：检索无证据、模型繁忙、模型不可用、生成超时、用户取消和网络断开。

## 可观测性

Agent trace 新增：

- 请求模式、实际模型、上下文和 GPU 服务地址标识。
- 排队时间。
- Embedding 时间。
- 数据库和向量检索时间。
- 证据整理时间。
- 模型加载时间和首 token 时间。
- Prompt token、输出 token、Prompt 速度和生成速度。
- 引用校验时间。
- 重试、超时、取消和模式切换。

健康接口同时报告 API、数据库、两个 Ollama 实例、三个模型、预热状态和队列容量。前端只有在这些检查满足相应条件时才能显示“所有服务正常”。

## 性能目标

以下目标以模型已预热且不包含排队时间为准：

| 指标 | 快速 14B | 深度 27B |
| --- | ---: | ---: |
| 首个阶段反馈 | 不超过 2 秒 | 不超过 2 秒 |
| 首个回答文字 | 不超过 15 秒 | 不超过 25 秒 |
| 完成时间 P50 | 不超过 30 秒 | 不超过 60 秒 |
| 完成时间 P95 | 不超过 60 秒 | 不超过 90 秒 |
| 请求上下文 | 16K | 32K |

## 测试与验收

基准测试先记录当前约 290 秒的端到端请求，再按上下文、GPU 装载、Flash Attention、KV Cache、5 分钟热保留、流式综合和并发逐项测量。测试集包含：

- 20 个普通单文档问题。
- 10 个普通知识库检索问题。
- 10 个多文档比较或复杂证据问题。
- 中文和英文问题。
- 5 个用户并发请求。

功能验收要求：

- Embedding 始终使用 `qwen3-embedding:8b` 且维度正确。
- 快速模式始终使用 14B，深度模式始终使用 27B。
- 自动模式符合确定性路由规则。
- 新会话默认自动，已有会话恢复其模式。
- SSE 能发送阶段、路由、排队、token、引用和最终事件。
- 引用编号、文档、页码和原文链接正确。
- 深度模型繁忙时可继续排队或手动切换快速。
- 停止、断开和取消会释放队列及推理资源。
- 5 个并发用户不会导致 OOM、API 崩溃、会话串用或错误引用。
- 模型不可用时返回明确错误，不返回固定模板。

质量验收比较优化前后的事实覆盖、引用准确率和回答完整性。任何参数优化如果导致稳定 OOM、明显质量下降或 CPU 回落，则回滚该参数。

## 发布与回滚

发布顺序为：推理参数与双实例、模型路由、会话模式、流式生成、队列交互、健康状态与监控。每一步均保留独立开关。发布前在服务器本地入口验证，再验证密码网关和临时公网入口。

回滚不修改知识库数据。路由或流式链路异常时可切回现有非流式 Agent 请求；GPU 参数异常时恢复上一份 Ollama 环境配置；前端模式选择不可用时回到 `auto`。文档原始文件、解析结果、向量和历史会话不得因推理服务回滚而删除或迁移。

## 数据与安全边界

本设计不改变新上传文章的正式存储位置，也不将新文章写入备份目录。模型服务仅监听服务器本机回环地址，不直接暴露到公网。公网访问继续经过现有网关和业务认证。日志与 trace 不记录登录密码、完整会话令牌或未脱敏的服务密钥。
