## 开场（0:00 - 1:30）

大家好，今天给大家介绍一个我们自研的系统——**私有化科学文献检索问答系统**。

简单一句话定位：**这是一个跑在我们自己服务器上的 RAG 知识库**——你把文献传进去，它自动解析、切分、建索引，之后你可以像聊天一样问它问题，它给你带引用的、可溯源的答案。

和市面上直接用云端大模型做问答的方案相比，我们这个系统有三个核心特点：

第一，**数据不出内网**。从文档解析、向量化到模型推理，全部在本地完成，用的是本地部署的开源模型，文献内容不会经过任何第三方服务。

第二，**不是"关键词匹配 + 大模型抄答案"**。它有完整的工程链路——文档怎么解析、怎么分块、怎么检索、答案怎么验证，每一步都有机制保证质量，答完的每一句话都能追溯到原文的哪一页。

第三，**它不只是一个网页**。同一套引擎还接入了飞书机器人——你在群里 @ 它，发一份 PDF 进去就能入库，直接问问题就能回答。

接下来的二十分钟，我会按"**文献进来之后发生了什么**"这条主线，把系统的功能、流程和背后的设计挨个讲一遍，中间穿插现场演示。

【提示】如果听众里有非技术背景的人，多强调"上传→自动处理→聊天问答→引用溯源"这条用户可见的主线；后面技术细节可标注"这段偏实现"。

## 一、整体架构（1:30 - 4:00）

【PPT】放 runbook 第 0 节的三层架构图

先把整个系统的骨架讲清楚。它分三层，对应三条流水线：

**第一层：摄取流水线**——负责把一份 PDF 变成"机器可检索的知识"。处理一份文档要经过 8 个阶段：解析、修复、规范化、语义分块、上下文化、嵌入、建索引、激活。这个我待会儿演示的时候细讲。

**第二层：检索与召回层**——负责"理解你的问题，找到最相关的证据"。它的流程不是简单搜一下：先做论文级路由确定搜索范围，再按问题类型多路检索，补一条全库语义兜底路防锁错，最后融合排序、压进 token 预算。这一步决定答案的"弹药"够不够好，待会儿我用一张流程图细讲。

**第三层：Agent 编排 + LLM 层**——负责"组织证据、生成答案、并验证答案"。一个叫 Agent 的编排器控制整个流程：规划、检索、生成、验证、最多一次重试，每一步都有记录，你甚至能在前端看到它"思考"的实时过程。

【PPT】放技术栈清单：FastAPI（Python）｜PostgreSQL + SQLite-vec/pgvector 双向量后端｜Ollama（本地开源模型）｜原生单文件前端 SPA｜Redis 队列｜飞书开放平台

技术栈上，后端是 Python FastAPI；数据库用 PostgreSQL；向量检索双后端自动切换——连的是 PostgreSQL 就走 pgvector 扩展，本地开发与测试环境兜底走 SQLite 的向量扩展，检索逻辑同一套；模型推理全部走本地 Ollama，跑的是开源模型：生成用 qwen3.5，嵌入用 qwen3-embedding，还有专门的视觉模型和综合模型；前端是一个无框架、无构建的原生单文件页面；后台任务用 Redis 队列管理；另外还有独立的飞书机器人进程常驻。

部署上我们分两个环境：**dev 开发环境和 test 测试环境**，两套服务、两块 GPU 完全隔离，各自挂 systemd 管理，代码通过 GitHub 走发布流程。

【提示】这段控制在 2 分半内，不要逐项念技术栈，挑"PostgreSQL、Ollama 本地模型、原生前端、飞书机器人"这四个词讲即可。

好，上传成功了。大家注意看右上角——页面会自动跳到"运行"视图，这就是处理流水线的看板。

【提示】上传后立即切回讲解，别干等解析。解析需要几十秒到几分钟，正好利用这个窗口讲 8 阶段，讲完正好回来展示结果。如果现场网络/模型慢，先用附录 A 的备选策略。

【PPT】放 runbook 第 2 节的 8 阶段流水线 mermaid 图

现在它正在后台跑一条**8 阶段的摄取流水线**，我按顺序讲：

**第一阶段：解析（parse）。** 把 PDF 的文本内容提取出来。这里有一个很长的**回退链**：首选 MinerU 解析器，它是目前最强的开源文档解析工具；如果失败或质量不够，依次回退——先用 pypdf 做文本层审计，发现文本缺失就定向调用 Document Intelligence 视觉修复特定页，再不行就整篇视觉识别，最后还有 pypdf 兜底。整个链路是"失败即关闭"的——拿不到有把握的结果，宁可判失败重来，绝不让脏数据入库。扫描件、公式、表格都有专门的视觉模型处理路径。

**第二阶段：修复（repair）。** 解析出来的文本会有 OCR 错字、乱码、断行这类噪音，这里做清洗。

**第三阶段：规范化（canonicalize）。** 这一步关键——它把各种来源、各种格式的文档统一成一种**规范化格式**，并抽取表、图、公式这些结构化信息登记到专门的清单里，供后面检索时特殊对待。

**第四阶段：语义分块（semantic split）。** 这一步把长文档切成适合检索的块。它不是简单地按字符数切，而是**双层父子结构**——大块 500 到 1800 tokens 做上下文，小块 180 到 600 tokens 做精确检索，用嵌入模型算句子间的语义相似度，在语义断裂的地方切。切完后，每一块都带着全局的上下文信息，保证"单独拿出来也能看懂"。

【提示】如果看板显示解析已完成，现在切回来看结果，顺势讲 5-8 阶段。

【演示】回到运行看板，展示这条文档的处理状态（如已 completed），点开它
【演示】展示解析信息面板：解析器类型、质量评分、是否修复过页、警告数
【演示】（可选）点"M"按钮展示规范化 Markdown 产物

大家看，这条记录已经处理完了。处理完后还有一道**质量门**——九项检查，比如文字量是不是太少、分块数是不是为零、图有没有丢失，每一项都有阈值，不过关就标失败并记下原因，不会静默放行。这就是剩下的阶段——

**第五阶段：上下文化（contextualize）。** 给每个块补充文档级上下文，让块"自包含"。目前这一步的策略白名单是空的，处于通过性状态，我们保留了这个环节。

**第六阶段：嵌入（embed）。** 每个块用嵌入模型转成一个 2560 维的向量，存进向量库——这是后面语义检索的基础。

**第七阶段：建索引（index）。** 同时建词法索引和向量索引，**原子化发布**：每个版本的产物都带一个 SHA-256 指纹作为版本键，发布时整体切换，绝不出现"一半新一半旧"的中间状态。

**第八阶段：激活（activate）。** 上锁激活——数据库行锁保证并发下同一份文档只有一个版本在切换，用户查询永远只会打到完整一致的知识快照上。

这 8 个阶段全部由**后台任务队列**驱动——每个文档的每个阶段都是确定性的任务 ID，不会重复执行；断了能自动重试；一台 worker 串行跑，保证顺序。

【提示】到这里约 8 分钟。如果解析还没好，用一句话带过："这份还在处理中，我们先把机制讲完，回头再看它"——不要等。

## 三、检索与召回层（8:00 - 12:00）

【PPT】放 runbook 第 3 节检索全景 mermaid 图——指着图按"四步"讲

文档处理完，知识就绪了。现在进入核心环节——**检索**。你在对话框输入一个问题，系统怎么知道去哪找、找什么？真实流程是四步，我按顺序讲：

**第一步：论文级路由，先划范围。** 系统给项目里每篇论文打一个"和这问题相关"的分——问题里的词和论文的标题、别名、关键词、正文逐项比对：撞标题的词每个 3 分，撞别名的每个 5 分；如果问题点名了某篇论文的**主主题**，或者论文正文写着"本文提出了某某方法"而问题正好问它，直接加 12 到 18 分。总分过线才进候选。然后按分数关系做决策：问题明显指向某一篇，就**锁定**这一篇——后续检索只在它内部做，防止全库噪音干扰；问题像是跨论文比较，就放行多篇。

【PPT】放大跑分公式那部分，逐项指

**第二步：按问题类型，多路检索。** 划完范围，系统先判断这是哪类问题——表格查询、图表查询、普通科学问题，各有各的通道。表格类问题走**表格清单直查**通道，命中即返回，后面能又快又准答表格题，靠的就是这一步；普通科学问题走**通用文本通道**：问题先向量化，在向量库里找语义最近的块，同时做词法匹配，关键词命中的加分。

这一步有个**反直觉的设计**要特别讲：第一步的"锁定"虽然能防噪音，但**锁错了怎么办**？词法匹配对科学问题很"二值"——命中就排第一，miss 就完全看不见。所以我们加了一条**全库语义兜底路**：不管词法路由怎么锁，只要不是用户明确指定文档，总是再对全库做一次向量检索，结果最后一起融合排序。锁错论文时，正确答案不会被锁死。这个设计不是拍脑袋——我们专门做过归因实验：曾经"锁定后就跳过兜底路"，300 条公开评测里 68 条反而变差，实测数据把我们赶回了现在的方案。

**第三步：融合排序。** 各路结果合在一起排座次：向量相似度 10 倍加权当主分，词法命中给上限 1.6 的加分，**表格块额外 +40 特权**——表格信息密度高，宁可多给一次机会。然后去重、按项目隔离、按文档版本隔离，子块命中时把父块也带上——这样引用能精确定位到原文段落。

**第四步：压预算。** 所有候选塞进 **6000 token 的预算**，放不下的按分数淘汰；表格题放宽候选数，保证表格数据尽量完整。

【提示】约 10:00，现在提第一个问题。

【演示】切到"新聊天"（chat 视图，Agent 模式）
【演示】输入预置问题 A（见附录 B 问题清单，选"事实检索类"，如"XXX 方法在文献中是如何定义的"）
【演示】发送，观察路由标签出现，展示回答
【演示】回答出现后，指出引用上标 [1][2]，为后面溯源埋钩子

大家看，这个回答的每一句话后面都带着引用标号 [1]、[2]——**这就是刚才那套检索的证据，不是模型编的**。待会儿我演示怎么点开引用、定位到原文。

关于检索质量，说两个数字：我们在公开基准 SciFact 上测过——**nDCG@10 达到 0.85、召回率达到 0.94**，300 条科学论断零未召回。这个成绩说明检索层是经得起公开评测的。另外我们有内部 30 题固定回归集，每次改动全量跑，答错一题都不许发版。

## 四、Agent 编排与 LLM 层（12:00 - 15:30）

【PPT】放 runbook 第 4 节 Agent 主循环 mermaid 图

检索拿到证据后，谁来组织答案？这就是 Agent 编排层。先讲一个大前提：**这一层用的生成模型也是本地的**——qwen3.5，32K 上下文，跑在自己的 GPU 上，答案生成过程完全不经过外部网络。

Agent 的主循环是**确定性有界循环**，六个环节：

**路由（route）→ 规划（plan）→ 检索（retrieve）→ 作答（answer）→ 验证（verify）→ 重试（retry，最多一次）**

每一环都有边界：最多 8 步、最多 5 次工具调用、单次生成 2 万 token 预算、90 秒超时——不会死循环，不会无限烧资源。

关键在**作答路径**的设计，有三种，**由系统根据证据情况自动选择**：

第一条，**确定性表格直通**——如果你的问题正好命中表格清单，系统把表格数据直接按行拼装成答案，完全不走大模型生成。数值问答零幻觉，多少就是多少。

第二条，**RAG 直通**——证据充分、覆盖度高时，让模型基于检索结果直接生成，经过验证器检查后直接返回。快，一条路径走完。

第三条，**综合路径**——证据分散、需要跨文档推理时，走"事实优先"的综合器：它把检索到的证据按段落组织好，要求模型**只基于证据说话，证据没说的一律标注不确定**，并且有保真守卫——答案里出现的每一条陈述，都要能在证据里找到支撑，找不到就打回重写。

答完还要过**验证器**——纯规则、不用 LLM 给 LLM 打分的那种：检查有没有空答案、有没有编造结构、引用编号对不对得上、覆盖度够不够。不通过就带着反馈重试一次，最多一次。

【提示】约 13:30，现在提第二个问题——综合类/跨文档类，让听众看 thinking feed 和排队机制。

【演示】新会话，Agent 模式，输入预置问题 B（见附录 B，选"跨文档综合类"，如"综合比较 X 与 Y 两种方法"）
【演示】发送后指给听众看：顶部"正在分析…"、thinking-feed 里实时滚动的工具步骤（路由→检索→生成）
【演示】如果队列中有其他任务，指出排队面板：模型名 + 前方位置
【演示】答案出来后展示"证据组织"结构（结论 / 证据 / 不确定性 / 来源 分块样式）

大家看这里——它在回答之前，先把思考过程实时流出来了：先路由、再检索、再生成。这套交互是 **SSE 流式协议**做的：15 秒心跳保活，客户端点"停止"能真正取消生成。生成过程在本地模型上跑，所以整个链路里**没有任何一个环节把你的数据发到外部**。

回答完成后，整个"思考轨迹"会被**脱敏**后落库——审计日志里能看到它每一步用了什么工具、哪个模型、调了几次，但所有内容都会过滤掉敏感信息。

【PPT】模型分工小表：qwen3.5（生成/综合）｜qwen3-embedding（嵌入 2560 维）｜视觉模型（PDF 图像页）｜qwen3.5 batch（批量任务）

再强调一下**模型分工**：生成、嵌入、视觉、综合，各用各的模型，各配各的并行度——嵌入模型"用即卸、不用即走"，不占显存；生成模型单路租约串行，保证推理质量稳定。这块的调度是独立的运行时统一管理。

【提示】至此约 15:30。如果时间紧，把这段的"综合路径"细节压成一句带过。

## 五、前端与交互功能（15:30 - 17:00）

【PPT】放 runbook 第 6 节前端布局图

功能讲完，看交互层。前端是一个**单文件原生 JS 的 SPA**，无框架、无构建、无第三方依赖——这也是运维友好的一个点：一个 HTML 文件就是全部前端。

三个视图：**聊天、文档库、运行看板**，左上角切换。左边栏是会话历史，顶栏可以切换研究项目——每个项目是一个隔离的知识空间，文档、索引、会话互不串。

最有价值的交互是**引用溯源**，我现在演示。

【演示】回到刚才问题 A 的回答（或重新问一次）
【演示】点击答案里的引用上标 [1]（或来源区的溯源按钮）

## 六、飞书机器人（17:00 - 18:30）

【PPT】放飞书机器人架构简图：飞书群 → 长连接 → 机器人进程 → 内部 API → 同一套 RAG 引擎

这套能力不止藏在网页里。我们给它接了一个**飞书机器人**——你在飞书群里 @ 它，两个能力：

**第一，文件入库。** 在群里直接发一个 PDF 并 @ 它，机器人把文件收进"飞书收件箱"项目，走的就是刚才讲的同一套摄取流水线，处理完会回复你。

**第二，文本问答。** 直接 @ 它提问，它调内部 API 走 Agent 引擎，把带引用的答案发回群里；问题复杂时它会回一句"处理中"先安抚，处理完再发完整结果。

技术上是**长连接模式**：机器人进程通过 WebSocket 与飞书服务器常驻保持连接，事件即收即回执（3 秒内应答），断线自动指数退避重连、进程由 systemd 拉起，网络恢复自己活过来。不用公网回调地址，内网也能用。

接入方式也简单：飞书开放平台建应用、勾权限、把应用拉进群，配置文件里填群白名单和租户白名单——**只有白名单里的群能用**，安全边界明确。同一套账号体系还能做网页登录：飞书 OAuth 授权登录，登录态走 HttpOnly Cookie 双通道防 CSRF。

## 附录 D：Q&A 弹药库

**Q：为什么不用云端大模型？**
A：核心是数据私有化——文献内容不出内网。本地开源模型在质量与成本之间是可控的，且整个检索、验证链路对模型的要求是"可靠生成"而非"聪明"，工程质量由流水线保证。

**Q：准确率如何？答错了怎么办？**
A：三层保障——检索层 SciFact nDCG 0.85 / 召回 0.94；生成层保真守卫（每条陈述必须证据支撑）；交互层每句带引用可溯源。任何一题答错都能点开引用发现并修正。内部 30 题回归每次改动全量跑。

**Q：支持哪些文档格式？扫描件能处理吗？**
A：PDF、DOCX、TXT、Markdown。扫描件走解析回退链——MinerU → 文本层审计 → Document Intelligence 视觉修复 → pypdf 兜底，失败即关闭，宁可判失败重来也不入库脏数据。

**Q：数据量大了会怎样？**
A：PostgreSQL + pgvector 生产后端，任务队列 + 确定性任务 ID 支持断点续跑，worker 串行化保证顺序。当前项目按文档主题隔离，扩展是按项目维度横向走的。

**Q：前端为什么不用 Vue/React？**
A：单文件原生 SPA 是刻意取舍——零构建、零依赖、部署只需一个文件，对内部系统运维成本最低。功能密度换来了这一点。

**Q：现在的局限？**（诚实清单，挑重点）
A：① 答案无打字机流式效果（SSE 累积、整体渲染）；② 前端不渲染表格（文本形式展示）；③ 文档处理进度无自动轮询，需手动刷新；④ 上传文案"200MB"与后端 50MiB 限制不一致，以后端为准；⑤ 表格问答准确率尚未达到目标线（nDCG 0.85 量级，目标 0.86）。

**Q：多用户同时用会不会互相打扰 / 会不会爆显存？**
A：分两层：**会话层已隔离**——每个人的会话、提问轨迹按登录用户隔离，他人的会话一律按"不存在"处理，列表里只看得到自己的；**知识库层共享**——项目、文档、上传是所有登录用户共享的（文献本来就是团队资产）。显存上不用担心：生成模型是**串行租约**（并行度 1），几个人同时提问 = 排队等 GPU，前端会显示排队面板；嵌入模型**用即卸**（keep_alive=0），并发请求共享同一份已加载副本，不会每人加载一份；综合路径复用生成模型不额外加载。显存峰值是固定的，不随人数涨。

**Q：多用户之间能互相删东西吗？**
A：诚实说，当前版本是"登录门槛 + 误删确认"两层：登录才能用；删文档必须带项目校验（跨项目 404）、删主题必须输入 slug 确认。但**没有细粒度角色权限**——任何登录用户都能删任意文档/主题/会话，"只能删自己上传的"或"只读用户"这类 RBAC 是规划项，不在当前版本。

**Q：和 LangChain / Dify 这类现成框架的区别？**
A：现成框架是"组装"，我们这是"自研链路"——8 阶段流水线、双层语义分块、意图路由、保真守卫、纯规则验证器、原子版本发布，每一步都是为"科学文献、可溯源"这个场景定制实现的，且每一步都有测试和实测数据背书。

**Q：部署和运维成本？**
A：一台带 GPU 的 Linux 服务器即可。systemd 托管服务，健康检查 + 质量看板 API 支持监控，部署走 GitHub 发布流程。双环境（dev/test）隔离开发与测试风险。
